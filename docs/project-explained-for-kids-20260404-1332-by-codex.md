# 像给 12 岁孩子讲编程课一样，讲清楚这个项目

更新时间：2026-04-04 13:32 UTC

这篇文档不用很专业的词，尽量像上编程课一样，把这个项目讲清楚。

你可以把这个项目想成一座“小小英语工厂”。

这座工厂能做两件事：

1. 展示已经做好的英语场景
2. 把你新上传的一张图片，变成一个新的英语学习场景

比如你拍一张“我的书桌”的照片，这个系统会努力帮你做出：

- 一张场景背景图
- 几个可以点击的热点，比如 `book`、`lamp`、`desk`
- 每个热点的一句英文
- 配套的 mp3 音频
- 一个可以在小程序里直接打开的新页面

所以，这个项目不是“写死几个页面的静态网页”，而是“会自己做新场景的小程序系统”。

---

## 1. 先用最简单的话说：这个项目到底是什么

把它想成一个 4 个角色合作的故事：

1. 小程序前端
   - 像“餐厅前台”
   - 负责和用户说话
   - 负责展示页面
   - 负责让用户选图片、点击按钮、看到结果

2. 后端 API
   - 像“服务员”
   - 接收前台的请求
   - 把请求交给后面的工人
   - 再把结果送回前台

3. 场景生成引擎 `core100`
   - 像“聪明老师”
   - 看图片，猜这是什么场景
   - 找出图片里的东西
   - 写出英文单词和句子

4. TTS 语音服务
   - 像“配音员”
   - 把文字读成 mp3

最后，用户看到的就是：

```text
选图片 -> 上传 -> 等一会儿 -> 打开新场景 -> 点击热点听英语
```

## 3. 用户真正使用时，会发生什么

假设一个小朋友在小程序里拍了一张早餐照片。

这个系统会这样工作：

### 第一步：小朋友选择图片

在手机上：

- 打开“生成我的场景”
- 拍照或者从相册里选一张图
- 点击“上传并开始生成”

这一步只是“把图片送进工厂”。

### 第二步：后端把图片收起来

后端会做两件事：

1. 把原图存到服务器上
2. 给这张图发一个编号

就像快递站给包裹贴上：

```text
upload_20260404123000_xxxxxx
```

这样以后系统就知道“这一单是哪张图”。

### 第三步：后端新建一个任务

因为生成场景不是 1 秒钟就完成的，所以后端不会让前端傻等。

它会说：

```text
好的，我已经收到任务了
你的任务编号是：task_xxx
你过一会儿再来问我进度
```

这就叫“异步任务”。

意思就是：

- 先把任务排队
- 后台慢慢做
- 前台时不时来问“做完了吗”

### 第四步：worker 开始干活

worker 就像工厂里的工人。

它会做这些事：

1. 取出上传图片
2. 复制一份作为新场景的背景图
3. 调用 `core100` 看图识别
4. 让 `core100` 告诉它：
   - 这是什么场景
   - 图片里有什么物体
   - 每个物体在哪里
   - 每个物体配什么英文句子
5. 再调用语音服务，把文字变成 mp3
6. 最后把这些结果整理成小程序能直接显示的格式

### 第五步：小程序不停问“做好了吗”

前端不会一直等着不动。

它会每 2 秒问一次后端：

```text
任务现在是 queued 吗？
任务现在是 running 吗？
任务 done 了吗？
```

这就叫“轮询”。

就像小朋友站在厨房门口问：

```text
我的蛋糕烤好了吗？
我的蛋糕烤好了吗？
我的蛋糕烤好了吗？
```

### 第六步：场景做完了

一旦任务成功，后端会说：

```text
done
sceneId = scene_user_xxx
```

然后前端就会打开这个新的场景页面。

于是你就能看到：

- 背景图
- 热点框
- 英文单词
- 英文句子
- 音频播放

## 4. 这个项目为什么不再是一页一个死页面

以前很多小程序是这样的：

```text
早餐页 = 一个文件
动物园页 = 一个文件
卧室页 = 一个文件
```

这样的问题是：

- 想加一个新场景，就要新写一页代码
- 场景越来越多，文件越来越乱
- 用户上传自己的图片根本没法接

现在这个项目已经换成了“统一场景页”模式。

意思是：

- 所有场景都用同一套页面来显示
- 页面只负责“拿数据并画出来”
- 不管是公开场景还是用户自己生成的场景，都用同一套显示方式

这就像：

- 以前每本书都要做一个不同的书架
- 现在是做一个通用书架，什么书都能放

这就是为什么这个项目更像“系统”，而不是“几个零散页面”。

## 6. 小程序前端住在哪里

### 6.1 小程序总入口

文件：

- `/www/wwwroot/e.cps.vin/weixin-demo-01/app.js`
- `/www/wwwroot/e.cps.vin/weixin-demo-01/app.json`

你可以把它想成“学校大门”。

它负责：

- 小程序启动
- 准备全局配置
- 注册页面

### `app.js` 在做什么

这个文件里很重要的一件事是：创建 `debugUserId`。

为什么需要它？

因为现在还没有正式登录系统，所以后端需要一个“临时身份牌”，知道：

```text
这个私人场景属于哪个调试用户
```

所以 `app.js` 会：

1. 去本地缓存里找 `debugUserId`
2. 如果没有，就新建一个
3. 保存到小程序本地
4. 后面请求后端时带上它

你可以把它想成：

```text
每个调试用户先领一个临时学号
```

### `app.json` 在做什么

它像目录表，告诉小程序有哪些页面：

- 首页
- 场景库
- 创建场景
- 我的场景
- 统一场景详情页

## 8. 前端“怎么跟后端说话”

目录：

- `/www/wwwroot/e.cps.vin/weixin-demo-01/services/`

你可以把 `services/` 想成“小程序的电话本”。

里面存着：

- 该打哪个电话
- 怎么发请求
- 收到什么样的回答

### 8.1 `services/api.js`

这是基础电话工具。

它负责：

- 发普通网络请求
- 自动带上 `X-Debug-User-Id`
- 把后端返回的结果整理一下

相当于：

```text
打电话前先报上自己的名字
```

### 8.2 `services/upload.js`

这个文件专门负责传图片。

因为图片上传不能完全像普通 JSON 请求那样写，所以要单独封装。

它负责：

- 用 `wx.uploadFile`
- 把图片发给 `/api/uploads/image`

### 8.3 `services/task.js`

这个文件负责“任务相关的电话”：

- 创建任务
- 查看任务状态

### 8.4 `services/scene.js`

这个文件负责“场景相关的电话”：

- 公开场景列表
- 场景详情
- 我的场景列表

## 11. 后端怎么保存数据

当前这个项目为了先跑通功能，还没有上数据库，而是先用 JSON 文件做“小账本”。

你可以把它们想成几个记录本。

### 11.1 公开场景记录本

文件：

- `/www/wwwroot/e.cps.vin/weixin-demo-01/backend/data/scenes.json`

里面放的是系统自带场景。

比如：

- 早餐
- 动物园

### 11.2 上传记录本

文件：

- `/www/wwwroot/e.cps.vin/weixin-demo-01/backend/data/uploads.json`

- 哪个用户上传了什么图

### 11.4 生成场景记录本

## 13. worker 为什么像“工厂工人”

文件：

- `/www/wwwroot/e.cps.vin/weixin-demo-01/backend/app/worker_runner.py`

这个文件非常像一个一直在工厂里巡逻的工人。

它会不停检查：

```text
有没有新的任务在排队？
```

如果有，它就开始做。

它的大概工作流程是：

1. 取到一个任务
2. 找到对应的上传图片
3. 复制背景图
4. 调 `core100` 分析图片
5. 调 TTS 生成音频
6. 整理成前端能读懂的场景
7. 保存结果
8. 把任务标记成完成

所以你可以把 `worker_runner.py` 想成：

```text
谁在厨房里真正做菜的人
```

## 14. `core100` 为什么像“看图写作老师”

`core100` 不在这个仓库里，它在：

- `/www/wwwroot/e.cps.vin/core100`

你可以把它想成一个很会看图说话的老师。

它看到图片后，会试着回答：

- 这张图像什么场景？
- 图里有哪些明显物体？
- 每个物体英文怎么说？
- 给每个物体配一句例句
- 物体在图上的位置大概在哪里？

这就是为什么系统能从“一张普通照片”走到“一个英语学习场景”。

## 16. 为什么还需要 `scene_adapter.py`

文件：

- `/www/wwwroot/e.cps.vin/weixin-demo-01/backend/app/scene_adapter.py`

这个文件可以理解成“翻译官”。

因为：

- `core100` 说的是一种格式
- 小程序 runtime 页想听的是另一种格式

如果没有这个翻译官，前后两边就容易“说不到一起”。

它做的事情是：

- 改字段名字
- 整理热点结构
- 规范坐标
- 填上音频路径
- 组成统一场景协议

所以这个文件的作用就是：

```text
把 AI 说的话，翻译成前端听得懂的话
```

## 19. 这个案例最适合教孩子学到什么

如果拿这个项目给 12 岁孩子讲编程，最适合学这几件事：

### 19.1 页面不是乱写的，要分角色

不是所有代码都塞进一个文件。

而是：

- 页面代码管显示
- service 管请求
- 后端管处理
- store 管保存

这叫“分工合作”。

### 19.2 程序不只是“点一下马上有结果”

很多真实世界的程序都需要时间。

比如：

- 上传
- 排队
- 生成
- 完成

这就会出现：

- 任务状态
- 轮询
- 进度条

### 19.3 同一个页面可以显示很多不同内容

不是每个场景都写一个页面。

而是：

- 页面写一次
- 数据换一份
- 场景就变了

这叫“复用”。

### 19.4 AI 功能也要放进正常的软件结构里

AI 不是突然冒出来一段魔法。

它也要老老实实地：

- 接输入
- 产输出
- 被后端调用
- 被前端消费

这就是“把 AI 变成系统的一部分”。
