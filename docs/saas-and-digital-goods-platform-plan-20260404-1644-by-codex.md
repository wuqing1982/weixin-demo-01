# 微信小程序 + API + Worker 演进为通用 SaaS 与虚拟数字商品销售平台的建议方案

更新时间：2026-04-04 16:44 UTC

本文不是只讨论当前“英语场景生成小程序”本身，而是讨论如何把它升级为一个更通用的平台：

- 既能卖当前这类 AI 生成型产品
- 又能支持以后其他 SaaS 产品
- 还能支持虚拟数字商品的销售、交付和管理

目标是做成一个“通用模板”：

- 用户注册/登录
- 商品管理
- 支付与订单
- 权益发放
- 订阅与配额
- 多产品复用
- 多租户扩展

也就是：

**从“一个能跑的功能项目”，升级成“一个可卖、可计费、可复用的平台底座”。**

---

## 1. 我先给一个总判断

我的建议不是直接把当前项目上面“硬堆”支付、会员、商品表。

更稳的路线是：

1. 先把当前项目抽象成一个“应用模块”
2. 再在外面加一层“平台层”
3. 平台层统一负责：
   - 用户
   - 组织/租户
   - 商品
   - 订单
   - 支付
   - 权益
   - 配额
   - 账单
   - 分销/渠道
4. 业务应用只负责：
   - 自己的内容生产逻辑
   - 自己的 worker
   - 自己的业务页面

简单说：

- 平台层负责“卖”
- 业务应用负责“交付”

如果这一步不分开，后面每做一个新 SaaS 产品，都会重复写：

- 登录
- 支付
- 权益判断
- 订单系统
- 配额系统

这会很快失控。

---

## 2. 你现在的项目在平台里应该扮演什么角色

当前这个“英语场景生成”项目，将来不应该继续被看成“整个系统”。

更合理的定位是：

**它是平台上的一个 App/Product。**

也就是说，将来平台结构应该像这样：

```text
平台
├── 账号系统
├── 支付系统
├── 订单系统
├── 权益系统
├── 商品系统
├── 渠道系统
├── 运营后台
└── 业务应用
    ├── 英语场景生成
    ├── AI 图片讲解
    ├── AI 绘本生成
    ├── 数字素材下载
    └── 其他 SaaS/虚拟商品
```

所以你的当前项目未来应该被包成：

- 一个业务应用
- 一个内容生成引擎
- 一个交付容器

而不是继续承担整个平台职责。

---

## 3. 平台应该拆成哪几层

我建议至少拆成 5 层。

## 3.1 入口层

负责：

- 微信小程序
- H5 落地页
- 可能未来还有 PC 管理台

目的：

- 承接流量
- 展示商品
- 引导付费
- 提供用户入口

当前小程序就是这一层的一个入口。

## 3.2 平台 API 层

负责：

- 用户
- 登录
- 商品
- 订单
- 支付
- 订阅
- 权益
- 用量记录
- 账单
- 统一鉴权

这一层应该尽量通用，不和某个单一业务绑死。

## 3.3 业务 App 层

负责：

- 英语场景生成
- 某个 AI 内容产品
- 某个数字商品应用

这一层每个应用可以有：

- 自己的页面
- 自己的 worker
- 自己的业务表
- 自己的交付逻辑

## 3.4 Worker/异步处理层

负责：

- AI 任务
- 批处理
- 音频生成
- 图像生成
- 文件转码
- 大任务回调

你现在的 `worker_runner.py` 就是这一层的雏形。

## 3.5 存储与账务层

负责：

- 数据库
- 对象存储
- 文件归档
- 用量计量
- 账务流水

这里是平台的核心基础设施层。

---

## 4. 我建议你优先抽象的“通用能力”

这是最关键的部分。

如果想做成“以后所有 SaaS 和虚拟数字商品都能复用”的模板，优先抽象以下能力。

## 4.1 用户系统

必须具备：

- 用户注册
- 登录
- 微信登录
- 手机号绑定
- 邮箱绑定
- 密码登录或验证码登录
- 用户资料
- 账号状态
- 黑名单/封禁

建议设计：

- `users`
- `user_identities`
- `user_sessions`
- `user_profiles`

要点：

- 不要把“微信 openid”直接当全局用户主键
- 用户主键要独立
- 微信、邮箱、手机号只是身份绑定方式

这是为了以后能扩展：

- 多端登录
- 多平台统一账号
- 用户迁移

## 4.2 租户/组织系统

如果你只是卖给个人用户，这层可以先轻量化。

但如果你想面向：

- 机构
- 学校
- 工作室
- 企业客户

那么最好从一开始就预留：

- `tenants`
- `tenant_members`
- `tenant_roles`

这样以后同一个平台就能支持：

- 个人买
- 团队买
- 企业采购

## 4.3 商品系统

这个平台真正通用的关键，不是“支付”，而是“商品抽象”。

建议商品分成三层：

1. 产品 Product
   - 这是大类
   - 例如：
     - 英语场景生成器
     - 数字绘本生成器
     - 素材下载库

2. 套餐 Plan / SKU
   - 这是卖的具体规格
   - 例如：
     - 月付版
     - 年付版
     - 100 次包
     - 企业版

3. 权益 Entitlement
   - 这是用户买到后真正获得的能力
   - 例如：
     - 每月可生成 100 次
     - 可下载高清文件
     - 可商用
     - 可多人协作

建议表结构方向：

- `products`
- `product_skus`
- `product_prices`
- `entitlement_templates`
- `sku_entitlements`

重点：

**不要把“价格”和“功能”写死在代码里。**

要让运营后台能配置。

## 4.4 订单与支付系统

至少需要：

- `orders`
- `order_items`
- `payments`
- `refunds`

支付方式建议分阶段：

第一阶段：

- 微信支付

第二阶段：

- 支付宝
- Stripe
- 线下转账/企业付款

订单状态建议明确：

- `pending`
- `paid`
- `failed`
- `closed`
- `refunded`
- `partially_refunded`

要点：

- 支付成功不等于交付成功
- 订单和交付要拆开

## 4.5 权益系统

这是 SaaS 平台和普通商城最大的区别之一。

因为用户不是只买“一个文件”，还可能买：

- 一个月会员
- 一年订阅
- 100 次额度
- 团队席位
- 解锁高级功能

所以建议单独做权益层：

- `user_entitlements`
- `usage_ledgers`
- `quota_buckets`

它负责回答这些问题：

- 这个用户有没有权限使用这个产品
- 还剩多少次生成
- 这个订单买到的权益什么时候过期
- 这个企业还有多少席位

## 4.6 用量与计费系统

如果你卖的是 AI 能力，必须认真做这层。

因为你的成本来自：

- 模型调用
- TTS 调用
- 存储
- 带宽
- worker 计算

所以要记录：

- 每次任务耗费了什么
- 每个用户用了多少次
- 每种套餐的毛利如何

建议有：

- `usage_events`
- `cost_events`
- `billing_snapshots`

不然你会卖着卖着发现：

- 订单很多
- 但不赚钱

## 5. 对“虚拟数字商品”要怎么抽象

你提到想支持“虚拟数字商品”。

这类商品和 SaaS 有相似点，但交付逻辑不同。

我建议把商品交付分成 4 种类型：

## 5.1 一次性交付型

例如：

- 下载一个素材包
- 下载一个模板
- 下载一套课程文档

特点：

- 买一次
- 交付一次
- 长期拥有或按授权使用

## 5.2 次数消耗型

例如：

- 购买 100 次生成额度
- 购买 50 次导出额度

特点：

- 每用一次扣一次

## 5.3 订阅型

例如：

- 月会员
- 年会员
- 企业包年

特点：

- 按时间有效

## 5.4 混合型

例如：

- 会员期间每月送 100 次额度
- 会员可低价追加购买次数包

这类混合型其实是最常见的。

所以商品系统设计时，不要只支持“买文件”，也不要只支持“按月订阅”。

必须能表达：

- 时间权益
- 次数权益
- 下载权益
- 商用授权

## 6. 当前这个英语场景产品可以怎么定价

我建议你不要一开始就做复杂价格矩阵。

先做 3 档就够：

## 6.1 免费体验版

建议：

- 每日 1 到 3 次生成
- 仅标准清晰度
- 不开放高级导出
- 带平台品牌水印或品牌露出

目的：

- 拉新
- 验证产品吸引力
- 让用户知道它能做什么

## 6.2 个人会员版

建议：

- 月付
- 年付
- 每月固定额度，比如 100 次
- 可下载无水印内容
- 可查看历史场景
- 可管理自己的内容库

目的：

- 面向普通家长、老师、个人创作者

## 6.3 专业/机构版

建议：

- 多账号协作
- 更高配额
- 内容归档
- 团队空间
- API 额度
- 更高并发
- 商用授权

目的：

- 面向学校、培训机构、工作室

价格层面我给你的原则建议是：

- 不要先拼低价
- 先把价值锚点做清楚
- 定价要跟“省下来的时间”和“可持续使用价值”挂钩

例如：

- 对个人，不是卖“一次生成”
- 而是卖“持续生成家庭英语学习素材的能力”

## 7. 更通用的平台，商品模型怎么设计

如果你希望未来支持所有 SaaS 和数字商品，我建议统一抽象成：

### Product

描述“这是一个什么产品”

例如：

- `english-scene-generator`
- `storybook-generator`
- `design-template-pack`

### SKU

描述“这个产品卖哪一种规格”

例如：

- `monthly-basic`
- `yearly-pro`
- `100-credits-pack`

### Delivery Strategy

描述“付款后怎么交付”

例如：

- `subscription_access`
- `credit_pack`
- `file_download`
- `license_unlock`

### Resource Type

描述“这个产品产出的是什么”

例如：

- `generated_scene`
- `audio_bundle`
- `download_file`
- `api_access`

有了这些抽象后，平台就能同时支持：

- 生成型产品
- 下载型产品
- 订阅型产品
- API 型产品

## 8. 技术架构建议：不要继续只用 JSON 文件

当前阶段你用：

- `uploads.json`
- `tasks.json`
- `generated_scenes.json`

是合理的，因为目的是先跑通。

但如果要做收费 SaaS，必须尽快升级。

建议演进路线：

### 第一阶段

当前状态：

- 小程序
- FastAPI
- 本地 JSON 索引
- 本地磁盘文件
- 单机 worker

适合验证产品。

### 第二阶段

升级成：

- PostgreSQL / MySQL
- Redis
- 对象存储
- 独立 worker

原因：

- 订单、支付、权益不能放 JSON
- 并发和一致性会出问题
- 文件也不适合长期放在站点目录

### 第三阶段

平台化：

- API 网关
- 多租户
- 独立管理后台
- 统一商品中心
- 统一支付中心
- 统一消息中心

---

## 9. Worker 建议怎么升级

你已经有 worker 雏形了，这是好事。

下一步建议是：

- 不再用进程内线程作为长期方案
- 升级为独立任务队列

可选方案：

- Celery + Redis
- RQ + Redis
- Dramatiq + Redis
- 自研轻量任务队列

原因：

- 任务可能会变多
- AI 任务时间长
- 支付后要触发异步交付
- 失败重试要标准化

worker 未来可以统一处理：

- 场景生成
- 图片压缩/转码
- TTS
- 导出
- 打包下载
- 邮件/短信/模板消息

## 10. 我认为你必须提前考虑的几个“非功能问题”

很多人做 SaaS，前面把功能做出来了，后面死在这些问题上。

## 10.1 成本控制

你这个业务有明确 AI 成本。

所以必须做：

- 单次任务成本估算
- 每用户成本统计
- 套餐毛利分析
- 超额后限流或加购

## 10.2 内容安全

用户上传图片，意味着一定会遇到：

- 不合规图片
- 版权风险
- 隐私风险
- 未成年人内容问题

所以建议：

- 上传审核策略
- 敏感词和风险标签
- 图片审核机制
- 举报与删除流程

## 10.3 交付可靠性

如果是收费产品，用户付费后任务失败会很麻烦。

所以要尽快做：

- 失败重试
- 任务补偿
- 退款逻辑
- 交付日志

## 10.4 数据归属和导出

对付费用户来说，未来一定会问：

- 我的内容是不是我的
- 能不能导出
- 账号注销后怎么办

这件事要在产品条款和技术设计里都考虑。

## 10.5 商业授权

虚拟商品特别容易碰到：

- 个人使用
- 教学使用
- 商用使用
- 二次分发禁止

所以商品模型里最好预留“授权类型”。

## 11. 平台后台应该有什么

建议至少有这几个后台模块：

1. 用户管理
2. 商品管理
3. 定价管理
4. 订单与支付管理
5. 权益与配额管理
6. 内容与资源管理
7. 任务监控
8. 财务和对账
9. 风控与审计
10. 渠道和推广

这意味着未来你可能至少有两个前台：

- C 端小程序
- 管理后台 Web

## 12. 推荐的 MVP 路线

如果让我来排优先级，我会这样做。

## 第一步：把当前业务变成“可收费单品”

先只服务一个产品：

- 英语场景生成

优先做：

- 用户登录
- 订单
- 微信支付
- 免费试用额度
- 付费配额
- 历史内容管理

不要一开始就做成“大而全平台”。

## 第二步：把“权益系统”独立出来

因为它是通用平台的核心。

只要权益系统独立出来，以后不管卖：

- 次数包
- 会员
- 文件下载

都能复用。

## 第三步：把“商品系统”独立成配置化

做到：

- 新增一个产品不需要改太多代码
- 配置 SKU 和价格即可上线

## 第四步：再做第二个业务应用

只有做出第二个业务应用，你才能真正验证“平台抽象是不是对的”。

否则你只是“为未来想象的平台”过度设计。

## 13. 我建议你现在就确定的几个核心原则

### 原则 1

业务应用和平台能力分离。

### 原则 2

商品、价格、权益不要写死在代码里。

### 原则 3

订单、支付、交付、用量必须拆开。

### 原则 4

用户主键独立，不直接依赖微信 openid。

### 原则 5

从现在开始预留多租户，但 MVP 不一定一次做全。

### 原则 6

worker 最终要独立，不把长期生命交给进程内线程。

### 原则 7

先做一个赚钱的单品，再验证平台能力，不要先做超级大平台再找产品。

## 14. 我对你这个方向的直接建议

如果你的目标是：

- 做可收费的 AI SaaS
- 卖虚拟数字商品
- 最后形成通用底座

那最实际的策略是：

1. 用当前“英语场景生成”作为第一个赚钱样板
2. 尽快加：
   - 登录
   - 支付
   - 额度
   - 历史内容
3. 同时把：
   - 商品
   - 权益
   - 订单
   - 用量
   抽象成平台层
4. 等第一个产品成交后，再复制到第二个产品

不要反过来。

不要先闭门造一个超级通用平台，再赌未来一定有很多产品能用。

正确顺序应该是：

**先有一个能赚钱的产品，再沉淀成平台。**

## 16. 一句话总结

你现在最应该做的，不是“把当前项目继续加一点支付功能”，而是：

**把当前项目重新定位为平台上的第一个付费业务应用，然后围绕它抽象出通用的用户、商品、订单、支付、权益和用量体系。**

这样未来你卖的不只是“一个小程序功能”，而是：

**一套可复用的 AI SaaS 与虚拟数字商品平台底座。**
